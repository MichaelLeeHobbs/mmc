# Rhino Compatibility Report

- **Target:** Mirth Connect 4.5.2 (`nextgenhealthcare/connect:4.5.2`)
- **Rhino engine:** `rhino-1.7.13.jar`, implementation version: `Rhino 1.7.13 2020 09 02`
- **Generated by:** `pnpm run rhino:compat` (scripts/rhino-compat.mjs)
- **JavaScript language version is configurable in Mirth.** `MirthContextFactory`
  sets the Rhino `Context` language version from the server setting
  **`rhinoLanguageVersion`**, which **defaults to `Context.VERSION_DEFAULT` (0)**.
  ES6 syntax (e.g. `let`, object destructuring) requires raising it; set
  **`rhinoLanguageVersion` to `200` (VERSION_ES6)** to enable the ES6 column below.

Columns are Rhino language versions: **0 = VERSION_DEFAULT (Mirth default)**,
**180 = VERSION_1_8**, **200 = VERSION_ES6**.

Legend: ✅ supported / spec-correct · ⚠️ partial or non-spec behavior · ❌ not supported / throws

> **Scope caveat:** probes run against a bare Rhino scope (`ImporterTopLevel`, which provides `importPackage`/`importClass`). This measures the **engine**: JavaScript syntax/semantics and the standard library. Mirth additionally injects channel globals (`msg`, `connectorMessage`, `$c`, `ChannelUtil`, the `userutil` classes, …) and its full server classpath — those are **not** measured here. So the language/syntax rows are authoritative for Mirth; the Java-interop rows reflect only the JDK + Rhino, not Mirth's added libraries.

## Gotchas

High-value warnings for script authors writing JavaScript in Mirth channels.
Remember that **Mirth defaults to `rhinoLanguageVersion = 0` (VERSION_DEFAULT)**,
so unless your administrator raised it, the **v0 column is what you actually get**.

### `let` / `const` availability and block scoping

- `let` is **NOT available** at v0 (default), available at v180, and available at v200.
  - At v0, `let` fails: `SyntaxError: missing ; before statement`. Use `var` unless `rhinoLanguageVersion` is raised.
- `const` is **available** at v0 (default).
- Block scoping (a `let` inside `{ }` not leaking out): v0 ❌, v180 ✅, v200 ✅. Detail @v200: block-scoped, did not leak.

### Loops: `let`/`const` per iteration (the reported gotcha)

- **`for (let i ...)` closure capture:** v0 ❌, v180 ⚠️, v200 ⚠️.
  - v0 (default): SyntaxError: missing ; after for-loop initializer
  - v180 (1.8): captures final value (3,3,3) - not per-iteration
  - v200 (ES6): captures final value (3,3,3) - not per-iteration
- **`const` re-declared each loop iteration** (`for (var k...) { const c = k; }`): v0 ✅, v180 ✅, v200 ✅.
  - v0 (default): no redeclaration error across iterations
  - v180 (1.8): no redeclaration error across iterations
  - v200 (ES6): no redeclaration error across iterations
- **`for (const x of ...)`** per-iteration const: v0 ❌, v180 ❌, v200 ❌.

### Destructuring: array vs object differ at the default version

- **Array** destructuring (`var [a,b]=[1,2]`): v0 ✅, v180 ✅, v200 ✅.
- **Object** destructuring (`var {a}=o`): v0 ❌, v180 ✅, v200 ✅.
  - **Surprise:** at the default v0, **array** destructuring works but **object** destructuring does NOT. Authors targeting default Mirth must avoid `{ }` destructuring.

### Template literals do not interpolate

- Template literal interpolation (`\`${x}\``): v0 ⚠️, v180 ⚠️, v200 ⚠️.
  - v0 (default): parsed but produced "val=${tx}" (no interpolation)
  - v180 (1.8): parsed but produced "val=${tx}" (no interpolation)
  - v200 (ES6): parsed but produced "val=${tx}" (no interpolation)
  - **Do not rely on backtick `${...}` interpolation in Mirth.** Use string concatenation (`'a' + x`) instead.
